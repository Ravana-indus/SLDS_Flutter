This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Flutter component library for **SLDS** — the design system for Sri Lanka's government digital services (GovTech Sri Lanka) — plus a Widgetbook preview app and an example consumer app. A [Dart pub workspace](https://dart.dev/tools/pub/workspaces) managed with [Melos](https://melos.invertase.dev), three workspace members:

```
packages/slds_components/   # the published package: design tokens, theme, widgets, l10n
widgetbook/                 # Widgetbook preview app — browse slds_components in isolation
app/                        # example Flutter app — consumes slds_components, bloc + clean architecture
```

`slds_components` has no dependency on the other two. `widgetbook` and `app` both depend on it via a workspace path dependency (`slds_components: {path: ../packages/slds_components}`), so local edits to the design system are picked up immediately by both without publishing.

## Commands

```sh
dart pub get           # or: melos bootstrap — resolve all 3 packages at once
melos run gen           # dart run build_runner build -d — regenerate widgetbook/lib/main.directories.g.dart
melos run widgetbook     # flutter run -d chrome — launch Widgetbook
melos run test            # flutter test in every package that has a test/ dir
```

`melos run test` prompts interactively to pick a package if run without a TTY — run tests per-package directly instead when scripting:

```sh
(cd packages/slds_components && flutter test)
(cd app && flutter test)
flutter test test/slds_button_test.dart   # single test file, from inside the package dir
```

Lint (per package, from inside its directory — there's no root-level `analysis_options.yaml`):

```sh
flutter analyze
```

Run the example app:

```sh
cd app && flutter run        # pick a device/simulator, or -d chrome
```

Regenerate localizations after editing `packages/slds_components/lib/src/l10n/*.arb`:

```sh
cd packages/slds_components && flutter gen-l10n
```

## Architecture

### packages/slds_components

The design system. Everything public is re-exported from `lib/slds_components.dart` — when adding a widget or token, export it there too or consumers can't see it.

- Raw design tokens (spacing, sizes, radii, elevation, opacities, durations, breakpoints, color hex ints) now live in the separate `packages/slds_tokens` package — pure Dart, no Flutter/`dart:ui` import, enforced by `packages/slds_tokens/test/dependency_direction_test.dart`. `slds_components` wraps those into Flutter types under `lib/src/theme/` (`slds_tokens.dart`, `slds_design_tokens.dart`).
- `lib/src/theme/slds_theme.dart` — `SldsTheme.light` / `.dark` / `.highContrast` are cached `static final ThemeData` (not methods, so a consuming app assigning them to `MaterialApp.theme` doesn't rebuild the theme every frame), with `useMaterial3: true` pinned and every `ColorScheme` role set explicitly (no `ColorScheme.fromSeed`).
- `lib/src/widgets/` — ~50 widgets (`SldsButton`, `SldsCard`, `SldsFab`, `SldsTextField`, `SldsDatePicker`, `SldsSummaryList`, etc. — see `lib/slds_components.dart` for the full export list). Widgets resolve color from the ambient `Theme`'s `ColorScheme` only; there is no per-instance `color` override param — that capability was deliberately removed as a breaking change to comply with the engineering guidelines' "no per-instance color overrides without architecture sign-off" rule (see `packages/slds_components/CHANGELOG.md`). Theming a single component goes through its `ThemeExtension` (e.g. `SldsFabTheme`), not a widget param.
- `lib/src/l10n/` — source `.arb` files (en/si/ta) and generated delegates under `gen/`. Ships strings only for the few labels components themselves own (e.g. the `SldsButton` loading-state accessibility announcement). Host apps must install `SldsLocalizations.localizationsDelegates`/`.supportedLocales` alongside their own. **The si/ta translations were machine-drafted, not reviewed by a speaker — verify before shipping.** Sinhala/Tamil text uses `Noto Sans Sinhala`/`Noto Sans Tamil` as a font fallback in `SldsTypography`; the font asset files aren't bundled yet.

Adding a component: put the widget under `lib/src/widgets/`, export it from `lib/slds_components.dart`, add a `@widgetbook.UseCase` in `widgetbook/lib/use_cases/`, then `melos run gen`.

### widgetbook

Preview app, one use-case file per component under `lib/use_cases/`. `lib/main.dart` wires the full addon toolbar: **Theme** (Light/Dark, defaults Light), **Locale** (en/si/ta), **Viewport** (freeform + every built-in device preset — this is the "run on an emulator" view; Widgetbook itself already runs as a normal web app via `flutter run -d chrome`, so there's no separate web target), **Alignment**, **Text Scale** (0.5×–2.0×), **Grid**, **Inspector**, **Zoom**. `lib/main.directories.g.dart` is generated by `melos run gen` — don't hand-edit it.

### app

Example Flutter app demonstrating how a real consumer uses `slds_components`, structured as **Clean Architecture** (domain/data/presentation per feature) with **flutter_bloc**. Currently a skeleton with one demo feature (`home`, a theme-mode toggle) meant to be deleted once real features exist.

```
lib/features/<name>/
  domain/         # entities, use cases, repository interfaces — no Flutter/HTTP/DB imports
  data/           # repository implementations, data sources — only add if the feature needs one
  presentation/
    bloc/         # Cubit/Bloc — holds UI state, calls domain use cases
    pages/        # widgets — render state, dispatch events, built from slds_components widgets
lib/main.dart      # composition root — builds use cases, provides blocs via BlocProvider
```

Dependencies point inward: `presentation → domain`; `data` would depend on `domain` (implementing its interfaces) if a feature needs persistence, never the reverse; `domain` never imports Flutter. Only add the sub-folders a feature actually needs — don't scaffold an empty `data/` for a feature with no data source.

No DI container (get_it, injectable, …) — `main.dart` constructor-injects use cases into blocs directly via `BlocProvider(create: ...)`. Reach for a DI container once wiring by hand there gets unwieldy, not before.
